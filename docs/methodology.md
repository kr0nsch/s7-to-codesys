# Методика миграции S7 (SCL) → CODESYS V3.5

Как переводить программы Siemens S7-300/400/1500 на CODESYS (целевой ПЛК — ОВЕН ПЛК210) с частичной
автоматизацией: что делает конвертер `s7conv`, что остаётся человеку, какие риски проверять и как
оценить трудоёмкость. Термины: **корпус** — исходники SCL, выгруженные из TIA Portal; **пометки** —
`// MIGRATION-CHECK` (переведено, проверить) и `// MIGRATION-TODO` (не переведено) в сгенерированном
коде; **сценарий** — входы блока по вызовам и ожидаемые выходы (CSV).

Принципы:

- **Перенос один к одному, а не переписывание.** Конвертер сохраняет структуру, имена и числа исходного
  блока: сгенерированный код сверяется с SCL построчно, а теги HMI и SCADA — по именам. Улучшения
  (рефакторинг, вынос констант, переименование по CONTRIBUTING.md) — отдельный этап после проверки
  поведения.
- **Ничего не теряется молча.** Всё, что не переводится однозначно, остаётся в коде пометкой с причиной
  и строкой исходника и попадает в отчёт [CONVERSION_REPORT.md](CONVERSION_REPORT.md).
- **Поведение проверяется по описанию логики, а не по результату конвертации.** Ожидаемые значения
  сценариев считают эталонные модели, написанные по нормативному описанию блока
  ([scenarios/README.md](../scenarios/README.md)).

## 2. Риски и как их закрывать

### Время цикла

- **S7:** OB1 выполняется в свободном цикле (с минимальным временем цикла, если задано), сторожевой
  таймер — максимальное время цикла CPU. **CODESYS:** `s7conv` по умолчанию ставит OB1 в циклическую
  задачу `MainTask` 10 мс (`--main-task freewheeling` — свободная, но её `tools/codesys` пока не создаёт).
  Период выбирают по реальному времени выполнения на ПЛК210 с запасом; сторожевой таймер задачи
  настраивают вручную.
- **Блоки, интегрирующие по периоду** (`FB_Totalizer`, `FB_PIController`, `FB_Ramp` получают период
  входом `cycleTime`): значение входа должно совпадать с периодом задачи, иначе ошибка интегрирования
  пропорциональна расхождению. В корпусе OB30 (100 мс) → задача `Task_OB30` 100 мс — сверить
  `cycleTime` в вызовах с `tools/codesys/config.json`.
- **Время счётом циклов** в исходнике (`counter := counter + 1` как время) при смене периода меняет
  поведение — st_lint помечает такие места (правило STL011) в рукописном коде; в сгенерированном их
  ищут по отчёту и обзору.
- **Проверка:** монитор задач CODESYS (время выполнения, джиттер) на ПЛК210, а не только на Control Win
  — у Control Win под Windows нет гарантий реального времени.

### Приоритеты OB и согласованность данных

- **S7:** OB1 — низший приоритет (1); циклические прерывания OB30–OB38 вытесняют OB1, их приоритеты
  задаются в свойствах OB (диапазон зависит от CPU — сверить с конфигурацией); OB100 выполняется один
  раз при переходе STOP → RUN до первого цикла OB1. **CODESYS:** приоритет задачи 0…31, 0 — высший
  (справка CODESYS 3.5.17, Task → Configuration). `s7conv` назначает циклическим OB приоритеты по
  периоду (короче период — выше), `MainTask` — 15.
- **OB100 эмулируется флагом первого цикла в `MainTask`** (`PRG_Startup` вызывается перед `PRG_Main`).
  Задача циклического прерывания с более высоким приоритетом может выполниться раньше первого цикла
  `MainTask` — если её код зависит от инициализации OB100, нужна блокировка по флагу запуска
  (пометка `ob.startup` в отчёте).
- **STOP → RUN — не то же, что Stop → Start CODESYS.** В S7 каждый переход STOP → RUN — тёплый пуск:
  нереманентные данные получают начальные значения, выполняется OB100, `Initial_Call` OB = TRUE. В CODESYS
  команда Stop останавливает задачи, а Start продолжает с текущими значениями переменных: флаг первого
  цикла (не RETAIN) сбрасывают только загрузка, Reset warm/cold и перезапуск ПЛК. Код OB100 после
  Stop → Start не выполнится — для объекта это проверяют отдельно (порядок ввода в работу после останова,
  пометки `ob.startup`, `ob.initial_call`).
- **Образ процесса.** В CODESYS все задачи делят один образ процесса, согласованным он бывает только
  для одной задачи (справка CODESYS 3.5.17, Task Configuration); в S7 у прерываний бывают свои разделы
  образа процесса. Входы, которые читают несколько задач, нужно проверить отдельно.
- **Общие данные задач.** Если циклическое прерывание и OB1 пишут одни и те же переменные, в S7 это
  часто «работало» из-за коротких критических участков. В CODESYS нужно осознанное решение: одна
  задача-писатель, копирование в начале цикла или блокировки.
- **Событийные OB** (диагностика OB82, аппаратные прерывания, ошибки) автоматически не переносятся:
  программа создаётся, задача по событию — вручную (`MIGRATION-TODO ob.event`). Стартовую информацию
  (`IO_State`, `Channel`, ...) операционная система CODESYS не заполняет: её передаёт вызов из
  рукописного обработчика события, поэтому у событийных OB она остаётся `VAR_INPUT` (в `VAR` программы
  извне записать нельзя — C0037). Источник события на ПЛК210 (диагностика модулей, флаги каналов) и
  способ вызова — [MANUAL_STEPS.md](MANUAL_STEPS.md), 4.1.

### Поведение retain при перезапуске

- **S7-1500:** в оптимизированных DB реманентность задаётся по переменной, в неоптимизированных — на
  весь DB; при тёплом пуске реманентные данные сохраняются, при сбросе памяти — нет.
- **CODESYS 3.5.17** (справка, Data Persistence): `RETAIN` сохраняется при аварийном выходе и
  Reset Warm, но **сбрасывается при повторной загрузке приложения, Reset Cold и Reset Origin**;
  `PERSISTENT` сохраняется и при загрузке и Reset Cold, сбрасывается только Reset Origin и при
  несовместимом изменении списка. Поэтому счётчики наработки и тоталайзеры, которые в S7 переживали
  загрузку изменений, в CODESYS переводят в `PERSISTENT` (`s7conv --retain persistent`; объект
  Persistent Variables создаётся вручную — `tools/codesys` в SP17 его не создаёт).
- **RETAIN в функциональном блоке:** в CODESYS в retain-память попадает весь экземпляр, а не только
  отмеченные переменные (пометка `section.fb_retain`, например `FB_Totalizer`) — проверить объём
  retain-памяти ПЛК210 по документации ОВЕН.
- **Неоптимизированный DB без NON_RETAIN** в S7 реманентен целиком — `s7conv` объявляет его `RETAIN`
  с пометкой `db.retain_standard`; так же — стандартные экземплярные и типизированные DB (секция
  `VAR_GLOBAL RETAIN` в `GVL_InstanceDBs`; в корпусе — `DB_LegacyTlg`).
- **Проверка на стенде:** выключение питания, Reset Warm, Reset Cold, повторная загрузка — по таблице
  ожидаемого поведения каждой реманентной переменной.

### Масштабирование аналоговых сигналов

- **S7:** номинальный диапазон канала — 0…27648 (перегрузка до 32511, ниже нуля — до −4864 для
  4…20 мА); NORM_X/SCALE_X без ограничения диапазоном. `F_NormX` и `F_ScaleX` (S7Compat) повторяют
  формулы Siemens, а `FB_AnalogIn` корпуса проверяет зоны перегрузки по сценариям CSV.
- **ПЛК210:** модули и встроенные входы ОВЕН отдают значение в своих единицах и диапазоне — сверить с
  документацией модуля и выбрать: либо масштабировать к 0…27648 в слое ввода-вывода (минимум правок в
  сконвертированном коде), либо заменить NORM_X/SCALE_X на масштабирование ОВЕН (правка блоков).
- **Адреса и порядок байтов:** S7 нумерует байты (`%IW64` — байты 64–65, старший байт первым),
  CODESYS — слова (`%IW32` — те же байты, на ПЛК210 младший байт первым). `s7conv` пересчитывает адреса
  (`GVL_IO`), но каналы на ПЛК210 привязываются в дереве устройств — адреса в `GVL_IO` только заготовка.
  Перекрытия разной ширины (`%MW10` и `%MD20` в S7 — пометка `addr.overlap`) меняют смысл из-за порядка
  байтов.

### Обмен с HMI

- Панели S7 обращаются к DB по символу или по абсолютному адресу (неоптимизированные DB), к меркерам —
  по адресу. В CODESYS доступ HMI — через символьную конфигурацию, OPC UA или Modbus; атрибуты
  `ExternalAccessible`/`ExternalVisible` переносятся только пометкой `decl.hmi_access` — видимость
  задаётся в символьной конфигурации.
- Старые панели на меркерах (`%MW`, `%M`) — `GVL_Markers` с `AT`: адреса пересчитаны, но порядок байтов
  в словах и двойных словах другой — проверить каждое слово, которое панель читает побитно.
- Глобальный DB → GVL с `qualified_only`: путь `"DB_Hmi".cmdWord` становится `DB_Hmi.cmdWord`;
  экземплярный DB → `GVL_InstanceDBs.DB_P101` (имя DB сохраняется).

### Теги SCADA

- Имена: `"DB_Plant".tankLevel` → `DB_Plant.tankLevel`, `"DB_P101".status.running` →
  `GVL_InstanceDBs.DB_P101.status.running`; переименования из-за ключевых слов CODESYS (пометка
  `name.renamed`) меняют имя тега. Таблицу соответствия тегов составляют по разделу «Подробно по
  файлам» отчёта конвертации (там строка «Блоки: DB → объект ST»).
- Протокол: драйвер S7 в SCADA заменяется на OPC UA или Modbus TCP — у каждого свои адреса и типы;
  `TIME` в CODESYS беззнаковый, в S7 — со знаком; `DT` вместо `DTL`.
- Архивы и тренды SCADA ссылаются на старые имена — переименование в SCADA планируют вместе с
  переключением, а не после.

| Счётчики CTU_INT и др. | PV/CV — INT (тип счётчика) | CTU: PV/CV — WORD | явные `INT_TO_WORD`/`WORD_TO_INT`, пометка `fb.counter` |

## 3. Проверка поведения: время в тестах

Сценарии CSV ([scenarios/README.md](../scenarios/README.md)) задают моменты вызовов `t_ms`, в том числе
строки ровно на пороге таймера (`boundary = TRUE`). TON/TOF/TP CODESYS Standard берут время из часов
ПЛК — тест не может поставить их на нужный момент. Рассмотрены два способа.

| Критерий | (а) моделируемое время | (б) реальное время, тест на много циклов |
|---|---|---|
| Как | таймеры сконвертированного кода читают подменяемый источник времени; тест ставит часы на `t_ms` перед каждым вызовом | строка выполняется в цикле, когда `TIME() − t0 >= t_ms`; тест длится, сколько длится сценарий |
| Детерминированность | полная: одинаковый результат при любой нагрузке | зависит от джиттера задачи; Control Win под Windows — без гарантий реального времени |
| Строки на пороге (`boundary`) | проверяются точно (`>=` ровно на PT) | не проверяются: момент вызова запаздывает на долю цикла |
| Длительность | все 39 сценариев — в первом цикле | самый длинный сценарий `FB_Sequencer/FullCycle` — 161 с: больше таймаута прогона тестов (`CDS_TEST_TIMEOUT_S` = 120 с); весь прогон — не меньше самого длинного сценария |
| Что проверяется | сконвертированная логика с таймерами S7Compat | сконвертированная логика с таймерами Standard |
| Цена | в рабочем коде — таймеры S7Compat вместо Standard; их совпадение со Standard нужно доказать отдельно | ничего не меняется в коде |

**Выбрано (а)** — оно надёжнее: проверяются все строки, включая пороговые, без ложных падений от
джиттера и за один цикл. Его слабое место — подменённые таймеры — закрыто тестами:

- `FB_S7Ton/FB_S7Tof/FB_S7Tp` (S7Compat) реализуют семантику МЭК 61131-3 и S7 с интерфейсом TON/TOF/TP
  (`IN`, `PT`, `Q`, `ET`), время берут из `F_S7Now()`: в работе это `TIME()` — тот же источник, что у
  Standard; при `GVL_S7Clock.xSimulation = TRUE` — моделируемые часы `GVL_S7Clock.tSimNow`.
- Юнит-тесты S7Compat (`tests/POUs/S7Compat`) проверяют пороги, фронты, сброс, PT = 0 и переход TIME
  через 2³² мс по описанию семантики, в том числе Q таймера TON при IN = TRUE дольше 2³² мс (ошибку
  первой версии `FB_S7Ton` нашёл тест `KeepsQWhileInHeldAcrossWrap`, добавленный ревью).
- Тесты `MatchesStandardInRealTime` (по одному на таймер) идут несколько циклов в **реальном** времени
  и сравнивают таймер S7Compat со Standard на одном входе в одних и тех же циклах: расхождением
  считается цикл, где ET различаются больше 5 мс или Q различается не на пороге PT. Так способ (б)
  используется там, где он силён, — для сверки с библиотекой, а не для логики блоков.

Конвертер включает таймеры S7Compat параметром `--timers s7compat`; `s7conv build-corpus` собирает
корпус именно так (по умолчанию `s7conv convert` даёт TON/TOF/TP Standard).

**Как устроен сгенерированный тест** (`s7conv gen-tests`, папка `tests/POUs/Scenarios`):

- один набор `FB_<Блок>_ScenarioTest` на CSV, один метод-тест на сценарий;
- у каждого сценария свой экземпляр блока в переменных набора (у ФБ с `VAR RETAIN` экземпляр не может
  быть временной переменной метода) — сценарий начинается с нового экземпляра, как требует формат;
- coUnit вызывает тесты каждый цикл, поэтому сценарий выполняется один раз по флагу `x<Сценарий>Done`;
  перед ним тест включает `xSimulation`, после — выключает: тесты в реальном времени в тех же циклах
  видят настоящие часы;
- строка: `tSimNow := T#<t_ms>MS`, присваивание изменившихся входов, один вызов, проверка каждого выхода
  (`AssertEquals_<тип>`; REAL/LREAL — с допуском из CSV). Ожидаемые значения — тексты ячеек CSV, это
  проверяет `s7conv/tests/test_testgen.py`;
- имена из CSV (имена SCL) переводятся в имена ST по таблицам конвертера: переименования и поля
  структур те же, что в сгенерированном коде; направление (вход/выход) и тип сверяются с объявлением;
- сообщения проверок уникальны (`Сценарий#строка путь`): coUnit не повторяет отчёт об одинаковых
  проверках, и одинаковые сообщения скрыли бы падения, а в итог теста попадает только текст сообщения
  (без Expected/Actual);
- набор укладывается в лимиты coUnit 1.2.0.0 (1000 проверок и 100 тестов на набор), которые библиотека не
  проверяет — лишнее пишется за границы массивов: генератор отказывается выпускать набор больше 900
  проверок или 100 тестов, такой CSV делят на несколько файлов. В корпусе самый большой набор — 470
  проверок, все 39 сценариев выполняются в одном цикле `TestTask` за 3 мс (TEST_REPORT.md).

**Предварительная проверка без CODESYS.** Интерпретатор ST в тестах конвертера
(`s7conv/tests/stsim.py`) исполняет сами сгенерированные наборы coUnit против закоммиченного
сконвертированного кода и слоя S7Compat — тем же разборщиком операторов, что и конвертер. Это модель
CODESYS (разрядность целых, float32 для REAL, семантика R_TRIG/F_TRIG задана явно), поэтому она не
заменяет прогон в Control Win, но ловит ошибки конвертера и генератора до него:

- все 39 сценариев (1895 проверок) проходят при семантике F_TRIG S7;
- при гипотезе «F_TRIG Standard: ложный спад на первом вызове» падает ровно один тест сценариев —
  `FB_PumpAlternation/RotateOnStop`, строка 1 (`leadPump` 2 вместо 1), и рукописный
  `StandardFTrigMatchesS7`; в CODESYS 3.5.17.30 оба прошли — гипотеза отвергнута, итог stsim и CODESYS
  совпал по всем 39 сценариям (TEST_REPORT.md, «stsim и CODESYS»);
- мутации логики (`>=` → `>` в пороге таймера, лишнее условие, неверный гистерезис, квитирование уровнем
  вместо фронта) роняют тесты. Мутация «квитирование уровнем» сначала прошла незамеченной — сценарии не
  различали фронт и уровень `ack`; в `FB_AlarmDelay` добавлен сценарий `AckHeldDuringActivation`, и теперь
  она ловится.

**Если тест расходится с CSV**, сначала сверяют описание логики в заголовке `.scl` — оно источник истины
и для эталонной модели, и для SCL. Дальше три варианта: ошибка конвертера (исправить `s7conv`, пересобрать
корпус), семантика платформы (решение в слое совместимости или пометка в MAPPING.md), ошибка модели или
описания (исправить описание, модель, CSV). Решение записывают в [TEST_REPORT.md](TEST_REPORT.md).

## 5. Оценка трудоёмкости

Отчёт конвертации даёт объём работы, а не часы: число конструкций по статусам и по правилам. Часы
получаются умножением на коэффициенты, которые **калибруют на пилотном блоке** — значения ниже
стартовые допущения автора, а не норматив.

```
T = N_auto · k_auto + N_check · k_check + Σ_r N_todo,r · k_r + T_интеграция + T_проверка + T_ПНР
```

| Слагаемое | Откуда N | Стартовый коэффициент (допущение, откалибровать) |
|---|---|---|
| `k_auto` — обзор автоматически переведённой конструкции | «Автоматически» в отчёте | 0,5–1 мин |
| `k_check` — разбор пометки MIGRATION-CHECK | «Требуют проверки» | 15–30 мин; у повторяющегося правила дорог только первый случай |
| `k_r` — ручной перевод MIGRATION-TODO по классам | таблица «Не поддерживается — причины» | системная функция (RD_SYS_T, RUNTIME, TypeOf): 1–4 ч; абсолютная адресация, `AT`, PEEK/POKE, `Any`/`Variant`: 2–8 ч; `GOTO` и метки: 1–3 ч на блок; событийный OB: 2–4 ч |
| `T_интеграция` | перечни из обследования | ввод-вывод, HMI, SCADA — по числу сигналов и экранов |
| `T_проверка` | число ключевых блоков | сценарии и эталонная модель — от нескольких часов на блок (зависит от числа режимов) |
| `T_ПНР` | объект | по опыту объекта; не выводится из отчёта |

Калибровка: на пилотном блоке типичной сложности фиксируют фактические часы по тем же слагаемым и
пересчитывают коэффициенты; затем оценивают остальные блоки. Доля автоматического перевода по
конструкциям завышает долю сэкономленного труда: самая дорогая работа — в немногих TODO (системные
функции, абсолютная адресация) и в интеграции, которой в отчёте нет.

**Пример — корпус `samples/scl`** (числа — из [CONVERSION_REPORT.md](CONVERSION_REPORT.md); коэффициенты —
стартовые из таблицы):

| Слагаемое | Объём | Оценка |
|---|---|---|
| Обзор автоматически переведённого | 942 конструкции | 8–16 ч |
| MIGRATION-CHECK | 26 пометок, 13 правил | 3–6 ч (дорог первый случай правила) |
| MIGRATION-TODO: системные функции и типы | 8 `func.unsupported`, 5 `type.unsupported`, 4 `decl.dropped_use`, 2 `call.param_dropped`, 1 `expr.eno` | 15–40 ч: в основном `FB_EventLogger` и `FB_LegacyTelegram` |
| MIGRATION-TODO: адресация и переходы | 2 `addr.unsupported`, 1 `addr.peripheral`, 2 `decl.at`, 2 `stmt.goto` + 2 `stmt.label` | 8–20 ч |
| MIGRATION-TODO: событийный OB | 1 `ob.event` (OB82) | 2–4 ч |
| Итого по коду | | ≈ 36–86 ч без интеграции, сценариев и ПНР |

Разброс большой, и это честный результат до пилота: два «трудных» блока корпуса дают больше половины
верхней оценки при 10 % конструкций.
