# Перенос своей программы S7 на CODESYS

Пошаговая инструкция для инженера, у которого есть проект TIA Portal с блоками на SCL: как выгрузить
исходники, сконвертировать их в ST CODESYS, прочитать отчёт, разобрать пометки `MIGRATION-CHECK` и
`MIGRATION-TODO`, проверить поведение тестами по сценариям и собрать результат в CODESYS. У каждого шага —
команда и вывод, который вы увидите на учебном наборе из четырёх файлов демокорпуса.

Здесь только работа с инструментом. Этапы миграции, риски (время цикла, приоритеты OB, retain, HMI, SCADA),
чек-лист и оценка трудоёмкости — в [methodology.md](methodology.md); действия в IDE (ПЛК210, OB82,
Persistent Variables, привязка ввода-вывода) — в [MANUAL_STEPS.md](MANUAL_STEPS.md).

## Что понадобится

| Что | Зачем |
|---|---|
| Python 3.11+ | конвертер `s7conv` использует только стандартную библиотеку; `requirements-dev.txt` нужен для проверок самого репозитория (pytest, ruff, mypy) |
| клон репозитория | `s7conv` работает из него: раскладку ST пишет общий модуль `tools/codesys/stlayout.py`, а объекты слоя совместимости S7Compat копируются из `src/` репозитория. `python -m pip install -e .` добавляет команду `s7conv`, но файлы по-прежнему берутся из клона |
| исходники на SCL | блоки LAD/FBD/STL `s7conv` не разбирает: их сначала переводят в SCL в TIA Portal или переписывают вручную |
| для шага 8: Windows, CODESYS 3.5.17.30 с CODESYS Control Win V3, библиотека coUnit 1.2.0.0 | сборка проекта и прогон тестов; установка — [MANUAL_STEPS.md](MANUAL_STEPS.md), раздел 1 |

```bat
git clone https://github.com/kr0nsch/s7-to-codesys.git
cd s7-to-codesys
```

Все команды ниже выполняются из корня клона (кроме шага 8: он начинается с перехода в каталог над клоном),
а свои файлы лежат внутри него, в каталоге `my_plc/` (имя любое). Пути пишите относительные и короткие:
генератор тестов вписывает путь к CSV в шапку набора, и длинный абсолютный путь не помещается в 120
символов строки (см. [«Частые ошибки»](#частые-ошибки)). Каталог `build/` в git не хранится.

## Учебный набор

Чтобы пройти шаги без своего проекта, возьмите четыре файла демокорпуса: типы UDT, насос `FB_Motor` (без
пометок), фильтр дребезга `FB_Debounce` (S5Time и F_TRIG — пометки `MIGRATION-CHECK`) и журнал событий
`FB_EventLogger` (системные функции S7-1500 — пометки `MIGRATION-TODO`), а также сценарии `FB_Motor`.

```bat
mkdir my_plc\scl my_plc\scenarios
copy samples\scl\UDT_PlantTypes.scl my_plc\scl\
copy samples\scl\FB_Motor.scl my_plc\scl\
copy samples\scl\FB_Debounce.scl my_plc\scl\
copy samples\scl\FB_EventLogger.scl my_plc\scl\
copy scenarios\FB_Motor.csv my_plc\scenarios\
```

То же в bash:

```bash
mkdir -p my_plc/scl my_plc/scenarios
cp samples/scl/{UDT_PlantTypes,FB_Motor,FB_Debounce,FB_EventLogger}.scl my_plc/scl/
cp scenarios/FB_Motor.csv my_plc/scenarios/
```

Выводы команд ниже получены на этом наборе (Windows 11, Python 3.12).

## 1. Выгрузка из TIA Portal

### Исходники блоков

В дереве проекта TIA Portal выделите блоки SCL (FB, FC, OB), блоки данных и типы данных PLC и выполните
«Generate source from blocks»; файлы сохраните в `my_plc/scl/`. Выгрузите всё, на что ссылаются
переносимые блоки: если типа ФБ или UDT нет во входе, ссылки на него переводятся по имени с пометкой
`MIGRATION-CHECK` (`type.unknown`, `call.instance_unknown`).

- **Расширения.** Из каталога конвертер берёт только `*.scl`. Источники DB и типов данных TIA Portal
  обычно сохраняет с расширениями `.db` и `.udt` — переименуйте их в `.scl`:

  ```bat
  ren my_plc\scl\*.db *.scl
  ren my_plc\scl\*.udt *.scl
  ```

  Файлы, переданные в командной строке по одному, читаются с любым расширением (`check`, `report`,
  `convert`), но генератор тестов и `build-corpus` принимают только каталог.
- **Кодировка** — UTF-8 (с BOM или без) или cp1251; переводы строк любые. Каталог читается рекурсивно,
  порядок файлов не важен.
- **Сверка с форматом.** Демокорпус написан по формату внешних источников TIA Portal V15–V18, но в TIA не
  компилировался ([samples/scl/README.md](../samples/scl/README.md)). Если ваша выгрузка не разбирается,
  шаг 2 покажет файл и строку.

### Таблица тегов

Символьные теги (`"P101_ThermalOk"`) и абсолютные адреса (`%I0.2`) конвертер сводит к одной переменной слоя
ввода-вывода `GVL_IO` и пересчитывает адреса в модель CODESYS (`%IW64` → `%IW32`). Для этого нужна таблица
тегов ПЛК в CSV — первая строка заголовок, как в `samples/scl/PlcTags.csv`:

```text
Name,Path,Data Type,Logical Address,Comment
EStop_Ok,IO_Inputs,Bool,%I0.0,Аварийный стоп не нажат (НЗ цепь)
P101_Fbk,IO_Inputs,Bool,%I0.1,P101 обратная связь контактора
```

- Обязательны столбцы `Name` и `Data Type`; `Logical Address` и `Comment` используются, если есть;
  столбец `Value` — значения констант пользователя. Русские заголовки (`Имя`, `Тип данных`, `Адрес`,
  `Логический адрес`, `Комментарий`, `Значение`) тоже распознаются.
- Разделитель — запятая, точка с запятой или табуляция; кодировка — UTF-8 или cp1251. Если TIA выгрузила
  таблицу в Excel, сохраните лист как CSV.
- Таблицу во входном каталоге конвертер находит сам — по заголовку; таблицу в другом месте передают
  ключом `--tags` (можно повторять).

### Конфигурация OB

Номер, вид и период OB TIA Portal во внешний источник не пишет. Положите рядом `ob_config.json` (его тоже
находят во входном каталоге; другой путь — `--ob-config`). Формат — как в `samples/scl/ob_config.json`:

```json
{
  "Main": {"number": 1, "kind": "main"},
  "Cyclic interrupt": {"number": 30, "kind": "cyclic", "interval_ms": 100},
  "Startup": {"number": 100, "kind": "startup"},
  "Diagnostic error interrupt": {"number": 82, "kind": "event"}
}
```

Ключ — имя OB из исходника (`ORGANIZATION_BLOCK "Main"`). `kind` — `main`, `cyclic`, `startup` или
`event`; `interval_ms` — период циклического OB; необязательные `priority` и `task` задают приоритет и
имя задачи CODESYS. Без файла номер ищется в имени или заголовке (`OB35`) и по стандартным именам TIA,
период — в имени и комментариях, иначе берутся значения S7-300/400 по умолчанию с пометкой
`MIGRATION-CHECK` (`ob.main`, `ob.cyclic`). Правила — [MAPPING.md](MAPPING.md), «OB и задачи».

Итог шага:

```text
my_plc/
  scl/          *.scl, таблица тегов *.csv, ob_config.json
  scenarios/    <Блок>.csv — сценарии поведения (шаг 6)
```

## 2. Проверка разбора

```bat
python -m s7conv check my_plc/scl
```

Увидите: `s7conv check: файлов 4, блоков 6, без ошибок`. Ошибки разбора выводятся в виде
`файл:строка:столбец: error: сообщение`, код выхода — 1. Разборщик восстанавливается после ошибки и
показывает все ошибки файла сразу. Что разбирается, но не переводится, и что не разбирается вовсе —
[GRAMMAR.md](GRAMMAR.md).

## 3. Оценка объёма до работ

```bat
python -m s7conv report my_plc/scl --md build/my_plc/report.md --html build/my_plc/report.html
```

Увидите:

```text
s7conv: отчёт записан: build/my_plc/report.md, build/my_plc/report.html
s7conv: конструкций 176: автоматически 164 (93 %), требуют проверки 6, не поддерживаются 6
```

Пути отчёта указывайте всегда: без `--md` и `--html` команда пишет в `docs/CONVERSION_REPORT.md` и
`build/report.html` относительно текущего каталога и в корне клона затрёт отчёт демокорпуса.

Как читать отчёт (Markdown и HTML одинаковы по содержанию):

| Раздел | Что в нём | Зачем |
|---|---|---|
| «Итог», «По видам конструкций» | число конструкций по статусам: блоки, объявления, операторы | общий объём; единица учёта — конструкция, а не строка |
| «По файлам» | то же по каждому файлу, доля автоматического перевода | какие блоки трудные |
| «Не поддерживается — причины», «Требует проверки — причины» | счётчики по правилам (`func.unsupported`, `type.s5time`, `fb.f_trig` …) | одно решение на правило, а не на каждую пометку |
| «Подробно по файлам» | строка исходника → статус → правило → причина; для DB — во что он превратился | связь пометки в коде с правилом; таблица соответствия тегов для HMI и SCADA |
| «Задачи CODESYS (из OB)», «Слой совместимости S7Compat» | задачи из OB и нужные объекты S7Compat | что появится в проекте кроме блоков |

Отчёт даёт объём работы, а не часы. Часы получаются по формуле из [methodology.md](methodology.md),
раздел 5 «Оценка трудоёмкости»: стартовые коэффициенты на конструкцию, на правило `MIGRATION-CHECK` и на
класс `MIGRATION-TODO`, откалиброванные на пилотном блоке. Для демокорпуса (998 конструкций) это ≈ 36–86 ч
только по коду, без интеграции, сценариев и пусконаладки. Доля автоматического перевода завышает долю
сэкономленного труда: самая дорогая работа — в немногих `MIGRATION-TODO` и в интеграции.

## 4. Конвертация

```bat
python -m s7conv convert my_plc/scl --out build/my_plc --folder Converted --timers s7compat --emit-support --report-html build/my_plc/report.html
```

Увидите:

```text
s7conv: файлов SCL 4, записано 19 файлов в build/my_plc
s7conv: конструкций 176: автоматически 164 (93 %), требуют проверки 6, не поддерживаются 6
```

Результат — тексты ST по файлу на объект CODESYS (контракт — [LAYOUT.md](LAYOUT.md)) и задачи из OB:

```text
build/my_plc/
  src/DUTs/Converted/      UDT и структуры: UDT_DeviceStatus.dut.st, ...
  src/GVLs/S7Compat/       GVL_S7Clock.gvl.st — часы для тестов
  src/POUs/Converted/      FB_Motor/FB_Motor.decl.st + FB_Motor.impl.st, FB_Debounce/, FB_EventLogger/
  src/POUs/S7Compat/       FB_S7Ton, FB_S7Tof, F_S7Now — рукописный слой совместимости
  tasks.json               задачи CODESYS из OB (формат — MAPPING.md, «OB и задачи»)
  report.html
```

Имена, числа и структура исходника сохраняются: код сверяется с SCL построчно, теги HMI и SCADA — по
именам. В заголовке каждого объекта — исходный файл и строки (`Источник: my_plc/scl/FB_Motor.scl, строки
41–157`), автор и версия блока S7.

| Ключ | Что делает | Когда нужен |
|---|---|---|
| `--out КАТАЛОГ` | каталог результата: в нём `src/` и `tasks.json` | всегда |
| `--folder Converted` | кладёт объекты в папку проекта `Converted`. Под неё настроен линтер (`tools/check/st_lint.toml`): правила имён CONTRIBUTING.md там не применяются, потому что имена S7 сохраняются | рекомендуется; так же собирается демокорпус |
| `--timers s7compat` | TON/TOF/TP → `FB_S7Ton/Tof/Tp`: время они берут из `F_S7Now()` — в работе это `TIME()`, тот же источник, что у Standard, а в тестах — моделируемые часы `GVL_S7Clock` | обязательно для тестов по сценариям (шаг 6) |
| `--emit-support` | копирует нужные объекты S7Compat (`F_NormX`, `F_ScaleX`, таймеры, `GVL_S7Clock`) из `src/` репозитория в результат | рекомендуется: без него в результате нет объектов, на которые ссылается код (конвертер их перечислит) |
| `--f-trig s7compat` | F_TRIG → `FB_S7FTrig` с семантикой S7 на первом вызове | если на вашей версии Standard падает тест `StandardFTrigMatchesS7` (на 3.5.17.0 проходит) |
| `--retain persistent` | реманентные данные DB → `VAR_GLOBAL PERSISTENT RETAIN` вместо `RETAIN` | данные, которые должны пережить загрузку приложения и Reset Cold ([MANUAL_STEPS.md](MANUAL_STEPS.md), 4.2) |
| `--main-task`, `--main-interval` | тип и период `MainTask` для OB1 (по умолчанию циклическая 10 мс) | если период главного цикла известен |
| `--tags`, `--ob-config` | явные пути к таблице тегов и конфигурации OB | если они не во входном каталоге |
| `--clean` | удаляет из `<out>/src` файлы `*.st`, которых нет в новом результате | повторная конвертация в тот же каталог |
| `--report-md`, `--report-html` | отчёт рядом с результатом | по желанию |
| `--fail-on todo` / `--fail-on check` | код выхода 1, если есть `MIGRATION-TODO` (или `TODO` и `CHECK`) | CI: новые неподдержанные конструкции не проходят незамеченными |

Почему таймерам S7Compat можно доверять: их юнит-тесты (`tests/POUs/S7Compat`) проверяют пороги, фронты,
сброс и переход TIME через 2³² мс, а тесты `MatchesStandardInRealTime` сравнивают каждый таймер со Standard
в реальном времени на одних входах; в CODESYS 3.5.17.30 все пройдены ([TEST_REPORT.md](TEST_REPORT.md)).
Обоснование выбора — [methodology.md](methodology.md), раздел 3. Все ключи — `python -m s7conv convert --help`.

## 5. Разбор пометок

Найдите все пометки (двоеточие в образце обязательно: без него совпадёт и строка-шапка каждого
сгенерированного файла, где перечислены оба вида пометок):

```bat
findstr /s /n /c:"// MIGRATION-TODO:" build\my_plc\src\*.st
findstr /s /n /c:"// MIGRATION-CHECK:" build\my_plc\src\*.st
```

```bash
grep -rn "// MIGRATION-TODO:" build/my_plc/src
grep -rn "// MIGRATION-CHECK:" build/my_plc/src
```

На учебном наборе — по 6 строк каждого вида. Так выглядят пометки в коде (номер в скобках — строка
исходника SCL):

```text
// FB_Debounce.decl.st — переведено, но смысл зависит от платформы:
    // MIGRATION-CHECK: S5Time → TIME: в S7 S5TIME — BCD с шагом 10 мс…10 с, диапазон до 2h46m30s (стр. 37)
    onDelayS5 : TIME := T#200MS;  // Задержка включения

// FB_EventLogger.impl.st — аналога нет, исходный текст закомментирован:
    // MIGRATION-TODO: RD_SYS_T: нет прямого аналога в CODESYS Standard (стр. 96)
    // #ret := RD_SYS_T(OUT => #nowDt);
```

Что делать с каждым статусом:

| Статус в отчёте | В коде | Что делать |
|---|---|---|
| автоматически | ST без пометок | обзор при сверке с SCL |
| требует проверки | `// MIGRATION-CHECK: причина (стр. N)` над переведённой строкой | найти правило в отчёте по номеру строки («Подробно по файлам»), принять решение один раз на правило — принять перевод, включить объект S7Compat ключом конвертера или переписать — и записать его в [ASSUMPTIONS.md](ASSUMPTIONS.md). Правила перечислены в [MAPPING.md](MAPPING.md), «Пометки MIGRATION-CHECK — сводка правил» |
| не поддерживается | `// MIGRATION-TODO: причина (стр. N)` и закомментированный исходник | написать вручную по описанию логики блока. Чем заменять — [MAPPING.md](MAPPING.md), «Не поддерживается (MIGRATION-TODO)»: системные функции → SysTime/CAA или `TIME()`, абсолютная адресация → символьная, `AT` → `UNION`, событийный OB → обработчик ([MANUAL_STEPS.md](MANUAL_STEPS.md), 4.1) |

Как вносить ручные правки, чтобы их не потерять:

- **Пока конвертация пробная**, сгенерированный код не правят: правка — в исходнике SCL (если конструкцию
  можно выразить иначе) или в ключах конвертера, затем `convert` повторяется.
- **Когда блок готов к ручной доработке**, его выносят из генерации: объект переносится в рукописную часть
  проекта, а его `.scl` убирается из входа, иначе следующая конвертация перезапишет правку. Блоки, которые
  на него ссылаются, после этого получат пометки `type.unknown` и `call.instance_unknown` — их нужно
  проверить. Решение записывают в ASSUMPTIONS.md (так требует методика, этап 4).

Конвертер помечает только то, что видно по тексту одной конструкции. Расхождения, которые проявляются во
время работы (разрядность промежуточных результатов, индекс вне границ, деление REAL на 0), он не
помечает вовсе — они в [MAPPING.md](MAPPING.md), «Расхождения, которые конвертер не помечает», и в
чек-листе [methodology.md](methodology.md), раздел 4.

## 6. Тесты поведения по сценариям

Сценарий — последовательность вызовов блока: входы по строкам и ожидаемые выходы после каждого вызова, по
одному CSV на блок (`my_plc/scenarios/<Блок>.csv`). Ожидаемые значения берут из описания логики блока
(функциональное описание, документация объекта, наблюдения на работающем S7), а не из результата
конвертации — иначе тест подтвердит ошибку конвертера. Полный формат — [scenarios/README.md](../scenarios/README.md).

Коротко о формате:

- заголовок — `scenario,cycle,t_ms,` затем столбцы `in.<имя>:<тип>` и `out.<имя>:<тип>`, в конце
  `boundary,comment`; имена — как в SCL, типы — CODESYS после конвертации (`TIME`, `UDINT` …);
- `t_ms` — моделируемое время вызова от начала сценария; строки с `boundary = TRUE` проверяют поведение
  ровно на пороге таймера, остальные отстоят от порога не меньше чем на 200 мс;
- у выхода типа REAL или LREAL сразу после него — столбец допуска `tol.<имя>`;
- каждый сценарий начинается с нового экземпляра; в первой строке заданы все входы.

Пример — сценарий фильтра дребезга, посчитанный вручную по описанию логики в заголовке
`FB_Debounce.scl` («выход TRUE после `onDelay` непрерывного сигнала, FALSE через `offDelay` после его
пропадания; `rising`/`falling` — импульсы по фронту и спаду»). Сохраните его как
`my_plc/scenarios/FB_Debounce.csv`:

```text
scenario,cycle,t_ms,in.raw:BOOL,in.invert:BOOL,in.onDelayS5:TIME,in.offDelayS5:TIME,out.debounced:BOOL,out.rising:BOOL,out.falling:BOOL,out.changeCount:UDINT,boundary,comment
OnOffDelay,1,0,TRUE,FALSE,T#1000MS,T#2000MS,FALSE,FALSE,FALSE,0,FALSE,сигнал появился: задержка включения пошла
OnOffDelay,2,500,TRUE,FALSE,T#1000MS,T#2000MS,FALSE,FALSE,FALSE,0,FALSE,0.5 с < 1 с: выход ещё FALSE
OnOffDelay,3,1000,TRUE,FALSE,T#1000MS,T#2000MS,TRUE,TRUE,FALSE,1,TRUE,ровно 1 с: выход TRUE и фронт
OnOffDelay,4,1600,FALSE,FALSE,T#1000MS,T#2000MS,TRUE,FALSE,FALSE,1,FALSE,сигнал пропал: задержка выключения пошла
OnOffDelay,5,3600,FALSE,FALSE,T#1000MS,T#2000MS,FALSE,FALSE,TRUE,2,TRUE,ровно 2 с после пропадания: выход FALSE и спад
```

Строка 1 заодно проверяет решение по пометке `fb.f_trig`: на первом вызове с `CLK = FALSE` спада нет
(`falling = FALSE`), как у S7.

```bat
python -m s7conv gen-tests my_plc/scenarios --out build/my_plc/tests --corpus my_plc/scl
```

Увидите: `s7conv gen-tests: наборов 2, тестов 8, проверок 384; рукописных наборов в PRG_Tests 0` (без
`FB_Debounce.csv` — наборов 1, тестов 7, проверок 364). В `build/my_plc/tests/POUs` появятся набор
`Scenarios/FB_<Блок>_ScenarioTest` (один метод-тест на сценарий) и программа запуска `PRG_Tests`.

Этот пример проверен генератором и интерпретатором ST из тестов конвертера (`s7conv/tests/stsim.py`):
набор проходит при семантике F_TRIG S7, а при гипотезе «ложный спад на первом вызове» падают проверки
строки 1. В CODESYS пример не запускался.

Что важно:

- `--corpus` — каталог ваших исходников SCL: по нему генератор сверяет имена и типы столбцов с
  объявлением блока и применяет те же переименования, что конвертер.
- Генератор всегда рассчитан на таймеры S7Compat: код для таких тестов конвертируйте с
  `--timers s7compat` (шаг 4), иначе тесты с таймерами не сойдутся.
- Набор не больше 900 проверок и 100 тестов (лимиты coUnit 1.2.0.0, которые библиотека сама не
  проверяет); больший CSV делят на несколько файлов.
- Шапка набора советует `python -m s7conv build-corpus` — это для репозитория с демокорпусом; для своего
  каталога после правки CSV повторите `gen-tests`.
- Для блоков со сложной логикой ожидаемые значения удобнее считать эталонной моделью на Python: примитивы
  таймеров и фронтов и запись CSV — в `scenarios/reference/scenario_lib.py`, примеры моделей —
  `scenarios/reference/model_fb_*.py`.

## 8. Сборка и тесты в CODESYS

`tools/codesys/cds.py` собирает проект CODESYS из `src/` и `tests/` корня репозитория через CODESYS
Scripting, задачи берёт из `tools/codesys/config.json`. Команда `build-corpus` пишет туда всё сразу, но
читает только `samples/scl` и `scenarios`. Поэтому проверенный путь — отдельная копия репозитория, в
которой демокорпус заменён своими файлами. Копию кладут рядом с первым клоном, а не внутри него: блок
начинается с `cd ..` из корня клона, и пути `..\s7-to-codesys\my_plc\…` указывают на первый клон (если вы
клонировали его под другим именем, поправьте их).

```bat
cd ..
git clone https://github.com/kr0nsch/s7-to-codesys.git my-migration
cd my-migration
git rm -q "samples/scl/*.scl" "samples/scl/*.csv" samples/scl/ob_config.json "scenarios/*.csv"
copy ..\s7-to-codesys\my_plc\scl\* samples\scl\
copy ..\s7-to-codesys\my_plc\scenarios\*.csv scenarios\
python -m s7conv build-corpus
```

Увидите на учебном наборе (с обоими CSV):

```text
s7conv build-corpus: записано файлов 8, удалено 114; файлов результата 35
s7conv build-corpus: конструкций 176: автоматически 164 (93 %), требуют проверки 6, не поддерживаются 6
s7conv build-corpus: тесты сценариев — наборов 2, тестов 8, проверок 384; рукописных наборов в PRG_Tests 7
```

`build-corpus` записывает:

- `src/{DUTs,GVLs,POUs}/Converted/` — сконвертированный код (лишние файлы из этих папок удаляются);
- `docs/CONVERSION_REPORT.md` — отчёт конвертации, `build/report.html` — его HTML-версия;
- задачи из OB — в `tools/codesys/config.json`, ключ `modes.normal.tasks` (остальной текст файла не
  меняется; `tools/codesys` создаёт только циклические задачи);
- `tests/POUs/Scenarios/` и `tests/POUs/PRG_Tests/` — тесты сценариев и программу запуска вместе с 7
  рукописными наборами слоя S7Compat из `tests/POUs/S7Compat`.

Настройки конвертации для `build-corpus` — функция `corpus_options` в `s7conv/corpus.py` (папка
`Converted`, таймеры S7Compat, F_TRIG Standard, `RETAIN`); например, для `PERSISTENT` там ставят
`retain_mode="persistent"`. Рукописные объекты `src/*/S7Compat` не удаляйте: без них сборка остановится с
ошибкой «нет рукописных объектов поддержки».

Дальше — CODESYS (установка и переменные `CODESYS_EXE`, `CODESYS_PROFILE` — [MANUAL_STEPS.md](MANUAL_STEPS.md),
раздел 1):

```bat
python tools\codesys\cds.py runtime init
python tools\codesys\cds.py build
python tools\codesys\cds.py check --tests
python tools\codesys\cds.py test
```

- `runtime init` — один раз: пользовательский процесс CODESYS Control Win V3 без прав администратора.
- `build` — рабочий проект `build\my-migration.project` с задачами из OB; компилируются только объекты,
  достижимые из задач. Если OB во входе нет, задач нет — тогда весь код проверяет `check --tests`.
- `check --tests` — компиляция всех объектов `src/` и `tests/`, в том числе без вызовов.
- `test` — тестовый проект с coUnit, загрузка в Control Win и прогон: ваши наборы сценариев и 7 наборов
  S7Compat; среди тестов S7Compat — `StandardFTrigMatchesS7`, сверка F_TRIG вашей версии Standard с S7.

На демокорпусе вывод такой (последние строки `cds.py test`): `[cds] build: OK (ошибок 0, предупреждений 0,
…)` и `[cds] test: OK (наборов 13, тестов 74, пройдено 74, упало 0, пропущено 0, …)`. Справочник команд и
переменных окружения — [tools/README.md](../tools/README.md), раздел «codesys/cds.py».

Честно о проверке этого шага: копия репозитория проверена до `build-corpus` включительно (файлы
записываются, задачи и тесты появляются). Сборка и тесты в CODESYS проверены на демокорпусе, а на чужих
исходниках этим путём не прогонялись.

Что ещё изменится в копии:

- Тесты pytest, привязанные к демокорпусу, упадут: в проверочной копии с учебным набором — 82 из 1030
  (`scenarios/reference/test_scenario_models.py` — эталонные модели демокорпуса, `samples/test_coverage_matrix.py`,
  моделирование сценариев и снапшоты корпуса в `s7conv/tests`, по одному тесту в `tools_project/` и
  `tools/tests/test_run_iec_checker.py`). Это проверки демонстрационных данных, а не конвертера: их удаляют
  или переписывают вместе с демокорпусом, иначе задание pytest в CI будет красным.
- `samples/scl/README.md`, `scenarios/README.md`, README и отчёты в `docs/` описывают демокорпус — их
  переписывают под свой объект.

Дальше — ручные шаги в IDE: обработчик событийных OB, объект Persistent Variables, привязка ввода-вывода
к ПЛК210 ([MANUAL_STEPS.md](MANUAL_STEPS.md), раздел 4) и чек-лист «После конвертации» в
[methodology.md](methodology.md), раздел 4.

Без отдельной копии `cds.py` можно направить на другой каталог переменными `CDS_REPO_ROOT` и `CDS_CONFIG`
([tools/README.md](../tools/README.md), «Переменные окружения»), но тогда задачи из `tasks.json` переносят в
свой `config.json` вручную. Этот вариант не проверялся.

## Частые ошибки

| Что видно | Причина | Что делать |
|---|---|---|
| `s7conv check` насчитал меньше файлов, чем выгружено | файлы `.db` и `.udt` из каталога не читаются | переименовать в `.scl` (шаг 1) |
| `s7conv: ошибка: нет входных файлов *.scl` | в указанном каталоге нет `*.scl` | проверить путь и расширения |
| пометки `type.unknown`, `call.instance_unknown` | во входе нет исходника ФБ или UDT, на который ссылается блок | выгрузить и добавить его исходник |
| `s7conv gen-tests: ошибка: …: строка длиннее 120 символов — укоротите имена` | путь к CSV вписывается в шапку набора, а каталог сценариев лежит вне текущего каталога или путь длинный | запускать из корня клона, сценарии держать внутри него, путь писать относительный (`my_plc/scenarios`) |
| тесты сценариев с таймерами не сходятся | код сконвертирован с таймерами Standard | конвертировать с `--timers s7compat --emit-support` (шаг 4) |
| изменился `docs/CONVERSION_REPORT.md` после `s7conv report` | `report` без `--md`/`--html` пишет отчёт туда | `git checkout docs/CONVERSION_REPORT.md`; указывать пути отчёта явно |
| `build-corpus: ошибка: нет рукописных объектов поддержки …` | удалены объекты `src/*/S7Compat` | вернуть их из git |
| `build-corpus: ошибка: имена сгенерированных объектов совпадают с рукописными …` | рукописный объект назван так же, как генерируемый | убрать `.scl` этого блока из входа или переименовать объект |
| `Filename too long` при `git clone` в Windows | длинный путь к каталогу клона: в репозитории есть пути длиной около 100 символов | клонировать в короткий путь (например, `C:\work`) или включить `git config --global core.longpaths true` |

Версии: `s7conv --version` и заголовки сгенерированных файлов показывают версию конвертера 0.1.0; версия
репозитория (выпуск на GitHub) — 1.0.0 ([CHANGELOG.md](../CHANGELOG.md)).
