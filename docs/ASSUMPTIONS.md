## Исходники и сборка

| № | Допущение | Статус | Обоснование / где проверить |
|---|---|---|---|
| B1 | Источник истины — тексты ST в `src/`, `.project` в git не хранится | принято | `.project` бинарный: его нельзя ревьюить и сливать. Готовые `.project` и `.library` прикладываются к релизам GitHub |
| B2 | Свойства в `build/assembled/` записываются в синтаксисе RuSTy: `PROPERTY_GET <Имя> : <тип> ... END_PROPERTY`, `PROPERTY_SET ...` | принято | В МЭК 61131-3 ред. 3 свойств нет; RuSTy понимает такой синтаксис. Собранный текст нужен только анализаторам и в CODESYS не импортируется |
| B3 | Вариант сборки `iec-checker` понижает конструкции, которые не разбирает iec_checker (методы внутри ФБ, `EXTENDS`, прагмы) | принято | Только для статанализа; семантика собранного текста может отличаться от исходной |
| B4 | GVL объявляются с `{attribute 'qualified_only'}`, обращение — `GVL_S7Clock.ИМЯ`, `DB_Plant.ИМЯ` | принято | Рекомендуемая практика CODESYS: нет конфликтов имён (в корпусе `heartbeat` есть и в `DB_Plant`, и в `DB_Telegram`). RuSTy не знает имён GVL — вариант сборки `rusty` убирает префикс, отсюда исключение `DB_Telegram` в `rusty_exclude.txt` |
| B5 | Конструкции CODESYS, которые не разбирает iec_checker 0.4 (`TIME()`, `a[i].b`, пустой оператор `;`, массив с начальным значением в структуре), не переписываются ради анализатора | принято | С 2026-10-16 их понижает вариант сборки `iec-checker` шаблона: `run_iec_checker.py --tests` — `ParserError` 0, обёртка проекта, которая допускала `ParserError` в шести описанных местах, удалена. Что понижение в этих местах скрывает и добавляет — [STATIC_ANALYSIS.md](STATIC_ANALYSIS.md), «Конструкции, которые раньше не разбирались» |
| B6 | Строковые литералы `STRING` (имена тестов, сообщения CfUnit) — только ASCII | принято | Кириллица в `STRING` зависит от кодовой страницы среды и рантайма. Комментарии остаются русскими |
| B7 | Обязательный статанализ в CI — iec_checker v0.4 (тот же, что локально); образ `nightly` — необязательное задание | принято | Обоснования в `iec_checker_allow.toml` подобраны под находки v0.4: с другой версией разборщика обязательная проверка зависела бы от его изменений. Бинарник v0.4 закреплён по размеру и SHA-256 (у релиза нет опубликованной суммы — она вычислена по файлу), образ `nightly` — по дайджесту |
| B8 | Библиотека Standard подключается плейсхолдером `Standard` (`libraries.standard` в `tools/codesys/config.json`, ключ в `library.libraries`): к рабочему и тестовому проектам и к проверке пула `cds.py library` | **подтверждено** | В config.json шаблона ссылки на Standard нет — первая сборка дала 89 ошибок (`Неизвестный тип: 'R_TRIG'`, `'TON'`, `'CTU'`, `CONCAT` не задан). Плейсхолдер разрешает профиль библиотек — Standard 3.5.17.0 (`effective_resolution` ссылки в собранном проекте, 2026-10-16), ссылка не qualified-only — `TON` без `Standard.` компилируется (tools/README.md). С ним сборка — 0 ошибок, 0 предупреждений (2026-10-16). С 2026-10-16 ссылка на Standard есть в шаблоне по умолчанию, тесты шаблона от config.json репозитория не зависят (STATIC_ANALYSIS.md) |

## Тесты (coUnit)

| № | Допущение | Статус | Обоснование / где проверить |
|---|---|---|---|
| C6 | Фреймворк тестов — CfUnit в актуальной версии 1.2.0.0, где он переименован в **coUnit** (co♻e). В коде пространство имён `coUnit`: набор — `FUNCTION_BLOCK ... EXTENDS coUnit.FB_TestSuite`; в методах-тестах — функции `coUnit.TEST('<имя>')`, `coUnit.TEST_FINISHED()` и методы базового ФБ `AssertEquals_<тип>(...)`, `AssertTrue/AssertFalse(Condition :=, Message :=)`; в `PRG_Tests` — `coUnit.RUN()` и флаг `AreAllTestsFinished()` | **подтверждено** | Синтаксис набора, `TEST`, `TEST_FINISHED`, `AssertEquals_INT/REAL`, `RUN` проверен зондом на CODESYS 3.5.17.30 (2026-10-15); `AssertEquals_BOOL/DINT/WORD/TIME/STRING/LREAL`, `AssertTrue/False` с этими параметрами собраны и выполнены в Control Win вместе со всеми наборами (2026-10-16, 74 теста). Сообщение о падении в итоге теста — только `Message`, без Expected/Actual |
| C7 | Параметры библиотеки coUnit — по умолчанию | **подтверждено** | Зонд 2026-10-15: с параметрами по умолчанию сборка на Control Win без ошибки C0106. Наибольший набор — `FB_AnalogIn_ScenarioTest`: 6 тестов, 470 проверок; пределы coUnit 1.2.0.0 по умолчанию — 1000 проверок и 100 тестов на набор (`GVL_Param_coUnit`), библиотека их не проверяет, поэтому генератор отказывается выпускать набор больше 900 проверок или 100 тестов. Последние проверки самых больших наборов выполняются и попадают в отчёт — проверено намеренным падением в копии репозитория (TEST_REPORT.md) |
| C10 | Раннер coUnit вызывает методы-тесты каждый цикл, пока набор не завершён; тест на несколько циклов завершается вызовом `TEST_FINISHED()` | **подтверждено** | Прогон в Control Win 2026-10-16: тесты `MatchesStandardInRealTime` (несколько циклов, ~700 мс) завершились и прошли, сценарии выполнились один раз по флагу; все наборы завершились за 1,2 с. Самый долгий цикл `TestTask` — 3 мс при периоде 10 мс (зонд) |
| C11 | Сообщения проверок уникальны внутри теста (`Сценарий#строка путь`) | принято | coUnit отслеживает проверки по сообщению, пути экземпляра и значениям и не повторяет отчёт об одинаковых: с одинаковыми сообщениями падение могло бы скрыться |

Пример шаблона (`FB_Example`, `F_Clamp`, `E_DeviceMode`, `I_Resettable`, `GVL_Const`, `PRG_Main` и их
тесты) удалён на этапе интеграции; его допущения C1–C5, C8, C9 и раздел «Семантика F_Clamp» — в истории
git (коммит создания репозитория из шаблона).
