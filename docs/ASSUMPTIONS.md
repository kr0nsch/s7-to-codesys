Сюда записываются решения, принятые без полной информации, и их обоснование. Если допущение
подтвердилось или опровергнуто — пометьте это здесь, а не удаляйте запись.

Статусы: **принято** — решение действует; **проверить** — нужна сверка с источником или прогоном;
**подтверждено** — проверено, указано чем.

## Исходники и сборка

| № | Допущение | Статус | Обоснование / где проверить |
|---|---|---|---|
| B1 | Источник истины — тексты ST в `src/`, `.project` в git не хранится | принято | `.project` бинарный: его нельзя ревьюить и сливать. Готовые `.project` и `.library` прикладываются к релизам GitHub |
| B2 | Свойства в `build/assembled/` записываются в синтаксисе RuSTy: `PROPERTY_GET <Имя> : <тип> ... END_PROPERTY`, `PROPERTY_SET ...` | принято | В МЭК 61131-3 ред. 3 свойств нет; RuSTy понимает такой синтаксис. Собранный текст нужен только анализаторам и в CODESYS не импортируется |
| B3 | Вариант сборки `iec-checker` понижает конструкции, которые не разбирает iec_checker (методы внутри ФБ, `EXTENDS`, прагмы) | принято | Только для статанализа; семантика собранного текста может отличаться от исходной |
| B4 | GVL объявляются с `{attribute 'qualified_only'}`, обращение — `GVL_S7Clock.ИМЯ`, `DB_Plant.ИМЯ` | принято | Рекомендуемая практика CODESYS: нет конфликтов имён (в корпусе `heartbeat` есть и в `DB_Plant`, и в `DB_Telegram`). RuSTy не знает имён GVL — вариант сборки `rusty` убирает префикс, отсюда исключение `DB_Telegram` в `rusty_exclude.txt` |
| B5 | Конструкции CODESYS, которые не разбирает iec_checker 0.4 (`TIME()`, `a[i].b`, пустой оператор `;`, массив с начальным значением в структуре), не переписываются ради анализатора | принято | Статанализ — через обёртку `tools_project/iec_checker_gate.py`: `ParserError` допускается только в местах из `tools_project/iec_checker_parser_gaps.toml` ([STATIC_ANALYSIS.md](STATIC_ANALYSIS.md)) |
| B6 | Строковые литералы `STRING` (имена тестов, сообщения CfUnit) — только ASCII | принято | Кириллица в `STRING` зависит от кодовой страницы среды и рантайма. Комментарии остаются русскими |
| B7 | Обязательный статанализ в CI — iec_checker v0.4 (тот же, что локально); образ `nightly` — необязательное задание | принято | Обоснования в `iec_checker_allow.toml` подобраны под находки v0.4: с другой версией разборщика обязательная проверка зависела бы от его изменений. Бинарник v0.4 закреплён по размеру и SHA-256 (у релиза нет опубликованной суммы — она вычислена по файлу), образ `nightly` — по дайджесту |

## Тесты (coUnit)

| № | Допущение | Статус | Обоснование / где проверить |
|---|---|---|---|
| C6 | Фреймворк тестов — CfUnit в актуальной версии 1.2.0.0, где он переименован в **coUnit** (co♻e). В коде пространство имён `coUnit`: набор — `FUNCTION_BLOCK ... EXTENDS coUnit.FB_TestSuite`; в методах-тестах — функции `coUnit.TEST('<имя>')`, `coUnit.TEST_FINISHED()` и методы базового ФБ `AssertEquals_<тип>(...)`, `AssertTrue/AssertFalse(Condition :=, Message :=)`; в `PRG_Tests` — `coUnit.RUN()` и флаг `AreAllTestsFinished()` | **подтверждено частично** | Синтаксис набора, `TEST`, `TEST_FINISHED`, `AssertEquals_INT/REAL`, `RUN` проверен зондом на CODESYS 3.5.17.30 (2026-10-15). Имена `AssertEquals_BOOL/DINT/WORD/TIME/STRING/LREAL`, `AssertTrue/False` и их параметры — по описаниям в кэше браузера установленной библиотеки coUnit 1.2.0.0 (`browsercache`); в сборке ещё не проверены |
| C7 | Параметры библиотеки coUnit — по умолчанию | **подтверждено** | Зонд 2026-10-15: с параметрами по умолчанию сборка на Control Win без ошибки C0106. Наибольший набор — `FB_AnalogIn_ScenarioTest`: 6 тестов, 470 проверок; предел проверок на набор (параметр `GVL_Param_coUnit`, у TcUnit по умолчанию 1000) — сверить, если наборы вырастут |
| C10 | Раннер coUnit вызывает методы-тесты каждый цикл, пока набор не завершён; тест на несколько циклов завершается вызовом `TEST_FINISHED()` | **проверить** | Так описано в документации TcUnit/coUnit и в описаниях `browsercache` (тест может требовать нескольких циклов ПЛК). На этом построены тесты сценариев (однократный запуск по флагу) и тесты `MatchesStandardInRealTime` (несколько циклов). Сверить при первом прогоне в Control Win |
| C11 | Сообщения проверок уникальны внутри теста (`Сценарий#строка путь`) | принято | coUnit отслеживает проверки по сообщению, пути экземпляра и значениям и не повторяет отчёт об одинаковых: с одинаковыми сообщениями падение могло бы скрыться |

Пример шаблона (`FB_Example`, `F_Clamp`, `E_DeviceMode`, `I_Resettable`, `GVL_Const`, `PRG_Main` и их
тесты) удалён на этапе интеграции; его допущения C1–C5, C8, C9 и раздел «Семантика F_Clamp» — в истории
git (коммит создания репозитория из шаблона).
