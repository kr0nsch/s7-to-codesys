# Ручные шаги

Что делает человек: установка CODESYS и coUnit, импорт в проект, сборка и тесты в CODESYS Control Win,
ручные объекты проекта. Всё, что выполняется без CODESYS (конвертер, линтер, статанализ, RuSTy), — в
[README](../README.md#быстрый-старт) и в CI; перенос своей программы S7 по шагам — в [USAGE.md](USAGE.md).

Команды CODESYS выполняет `tools/codesys/cds.py` (подробно — [tools/README.md](../tools/README.md),
раздел «codesys/cds.py»). Проект s7-to-codesys собран и протестирован в CODESYS 3.5.17.30 с
CODESYS Control Win V3 (2026-10-16): сборка — 0 ошибок и 0 предупреждений, тесты — 74 из 74, roundtrip без
диффа ([TEST_REPORT.md](TEST_REPORT.md)); ошибки сборки из IDE записываются в [BUILD_ERRORS.md](BUILD_ERRORS.md).

## 1. Установка

1. CODESYS V3.5 SP17 Patch 3 (3.5.17.30) с сайта ОВЕН с компонентом CODESYS Control Win V3.
2. Для ПЛК210 — пакет таргет-файлов ОВЕН («Инструменты → Установщик пакетов»); версию таргет-файла
   сверить с прошивкой ПЛК.
3. Библиотека coUnit 1.2.0.0 (CfUnit, MIT; в коде пространство имён `coUnit`) — в репозиторий
   библиотек `System`. Если её нет, `cds.py` установит её из файла, заданного переменной
   `COUNIT_LIBRARY`. Параметры библиотеки — по умолчанию: на Control Win проект собирается без ошибки
   C0106 (проверено зондом; [ASSUMPTIONS.md](ASSUMPTIONS.md), запись C7 о параметрах coUnit).
4. Переменные окружения пользователя (через `setx` их видит `cds.py` и без перезапуска консоли):

   | Переменная | Значение |
   |---|---|
   | `CODESYS_EXE` | путь к `CODESYS.exe` |
   | `CODESYS_PROFILE` | `CODESYS V3.5 SP17 Patch 3` |
   | `COUNIT_LIBRARY` | путь к `counit.library`, если библиотеки нет в репозитории |

5. Пользовательский процесс рантайма (без прав администратора): `python tools/codesys/cds.py runtime init`
   один раз, дальше `cds.py test` запускает рантайм сам.

## 2. Пересборка корпуса (если менялись конвертер, корпус или сценарии)

```bash
python -m s7conv build-corpus          # src/*/Converted, отчёт, задачи в config.json, тесты сценариев
python -m s7conv build-corpus --check  # то же без записи: код 1, если репозиторий устарел (так в CI)
```

Сгенерированное (`src/*/Converted`, `tests/POUs/Scenarios`, `tests/POUs/PRG_Tests`) руками не правится —
правка в IDE будет потеряна при следующей пересборке. Настройки сборки корпуса (таймеры, `F_TRIG`) — в
`s7conv/corpus.py` (`corpus_options`).

## 3. Импорт, сборка, тесты

```bat
python tools\codesys\cds.py build            :: src/ → build\s7-to-codesys.project, сборка
python tools\codesys\cds.py check --tests     :: компиляция всех объектов src/ и tests/ (и без задачи)
python tools\codesys\cds.py test             :: src/ + tests/ → тестовый проект, Control Win, coUnit
python tools\codesys\cds.py roundtrip        :: импорт → экспорт → побайтное сравнение с src/, tests/
python tools\codesys\cds.py report           :: итог прогона → docs/TEST_REPORT.md
```

- `build` компилирует только объекты, достижимые из задач; `PRG_Diagnostic_error_interrupt` (OB82) задачи
  не имеет, поэтому весь корпус и тесты проверяет `check --tests` («Проверить все объекты пула» во
  временном проекте без устройства; на диск ничего не записывается).
- Библиотека Standard подключается плейсхолдером `Standard` из `tools/codesys/config.json`
  (`library.libraries`); без неё сконвертированный код не собирается.

- Рабочий проект получает задачи из `tools/codesys/config.json` (режим `normal`): `MainTask` 10 мс
  (`PRG_Startup`, `PRG_Main`), `Task_OB30` 100 мс (`PRG_Cyclic_interrupt`). Тестовый — `TestTask` 10 мс
  → `PRG_Tests` и библиотеку coUnit.
- Артефакты: `build/build.log`, `build/build.json` (сообщения компилятора с файлом и строкой раскладки),
  `build/test-results.json`, `build/junit.xml`.
- Без лицензии Control Win работает 2 часа; `cds.py test` перезапускает рантайм, если он работает
  дольше 100 минут.

## 4. Что делается только в IDE

Рабочий проект `build/s7-to-codesys.project` нужен для проверки на Control Win: `cds.py import` приводит
его задачи к `config.json` (лишние удаляет) и сверяет устройство с `config.json`. Проект для ПЛК210
делается из него в IDE:

1. `python tools\codesys\cds.py build`, открыть `build\s7-to-codesys.project` в CODESYS 3.5.17.30,
   «Файл → Сохранить проект как…» — вне `build/` (например, `s7-to-codesys-plc210.project`; в git не
   хранится, прикладывается к релизу).
2. Устройство в дереве → «Обновить устройство…» → ПЛК210 с версией таргет-файла под прошивку.
3. Шаги 4.1–4.4.

В проект с другим устройством `cds.py import` не пишет (отказ «устройство проекта … не совпадает с
config.json»), а с переменными `CDS_DEVICE_TYPE`/`CDS_DEVICE_ID`/`CDS_DEVICE_VERSION` приведёт задачи к
`config.json` и удалит задачи, созданные в IDE (tools/README.md, «Импорт и экспорт: правила»). Поэтому
после пересборки корпуса изменения переносят в проект ПЛК210 по `git diff`, а задачи из 4.1 проверяют
после каждого импорта.

### 4.1 Диагностика OB82: обработчик события

Что есть в коде. `PRG_Diagnostic_error_interrupt` (папка `Converted`) — тело OB82: счётчик событий
`DB_Plant.diagCount`, канал `diagLastChannel`, состояние `diagIoState`. Стартовая информация OB —
`VAR_INPUT` `IO_State`, `Channel`, `MultiError`: CODESYS её не заполняет, её передаёт вызов из
обработчика. `LADDR` (`HW_ANY`) не перенесён, `DB_Plant.diagLastLaddr` не пишется. Задачи у программы нет
(в отчёте конвертации — `ob.event`, `ob.start_info`).

1. Выписать, что в S7 вызывало OB82 на этом объекте (обрыв или КЗ канала 4–20 мА, пропадание питания
   модуля и т. п.), и найти, чем то же событие видно на ПЛК210: статусы модулей и каналов в дереве
   устройств, диагностические биты каналов. Состав и имена — **сверить с документацией ОВЕН** на
   таргет-файл и модули.
2. Написать программу-обработчик (например, `PRG_DiagEvents`): по новому событию (фронт флага
   диагностики или смена кода состояния) она формирует стартовую информацию и вызывает

   ```
   PRG_Diagnostic_error_interrupt(IO_State := wIoState, Channel := uiChannel, MultiError := xMultiError);
   ```

   Такой вызов собран в CODESYS 3.5.17.30 без ошибок; запись `PRG_Diagnostic_error_interrupt.Channel := …`
   — ошибка C0037 (TEST_REPORT.md, «Повторная проверка с чистого `build/`»). Если обработчик читает
   объекты дерева устройств ПЛК210, в `src/` его не кладут — на Control Win он не соберётся.
3. Выбрать, откуда вызывать обработчик:
   - **из `MainTask`** (рекомендуется): «Конфигурация задач → MainTask → Добавить вызов» после
     `PRG_Main`. Обработчик работает в той же задаче, что и `PRG_Main`, — новых общих данных между задачами
     не появляется; задержка реакции — до одного цикла (10 мс);
   - **задачей по событию**: «Конфигурация задач → Добавить объект → Задача», тип «Событие», переменная
     события — глобальная `BOOL`, которую ставит обработчик в `MainTask` (задача срабатывает по её
     переднему фронту); стартовую информацию передать через глобальные переменные. `DB_Plant` тогда пишут
     две задачи — приоритет и защиту общих данных выбрать по [methodology.md](methodology.md), «Приоритеты
     OB и согласованность данных».
4. Решить, чем заменить `LADDR` (номер модуля или слота ПЛК210), и писать его в
   `DB_Plant.diagLastLaddr` из обработчика.
5. Проверить на стенде: вызвать событие (отключить датчик 4–20 мА, снять питание модуля) и убедиться, что
   `diagCount` растёт на 1 за событие, а `diagLastChannel` и `diagIoState` показывают канал и состояние.

### 4.2 Persistent Variables

Что есть в коде. Корпус собран с `RETAIN` (по умолчанию `s7conv`): `VAR_GLOBAL RETAIN` в `DB_Plant` и
`GVL_InstanceDBs` (`DB_LegacyTlg`, пометка `db.retain_standard`), `VAR RETAIN` в `FB_Totalizer` (в
retain-памяти весь экземпляр, пометка `section.fb_retain`). В CODESYS `RETAIN` сбрасывается загрузкой
приложения и Reset Cold, `PERSISTENT` переживает и их ([methodology.md](methodology.md), «Поведение retain
при перезапуске»).

1. Составить таблицу реманентности: для каждой реманентной переменной S7 — должна ли она пережить
   загрузку изменений и Reset Cold (тоталайзеры, наработка, счётчики пусков — обычно да).
2. Для таких данных сконвертировать с `--retain persistent` (`s7conv convert … --retain persistent`; для
   корпуса — `retain_mode="persistent"` в `corpus_options`, `s7conv/corpus.py`, затем
   `python -m s7conv build-corpus`). Реманентные данные глобальных DB получат `VAR_GLOBAL PERSISTENT
   RETAIN` и пометку `db.persistent`.
3. В IDE: «Приложение → Добавить объект → Persistent Variables». Скриптом в SP17 этот объект не создаётся
   (`cds.py import` предупреждает); созданный объект `cds.py` обновляет из `src/GVLs/<Имя>.pvl.st` и
   выгружает при `export`. Без него сборка даёт предупреждение C0244 «Приложение не содержит
   VAR_PERSISTENT-списка для ввода экземпляра пути для переменной …» (проверено в 3.5.17.30).
4. Внести в объект пути постоянных переменных (команда объекта «Добавить все пути экземпляров») и
   пересобрать: C0244 должно исчезнуть. Порядок действий и поведение для переменных внутри ФБ —
   **сверить со справкой CODESYS 3.5.17**, «Persistent Variables».
5. Не менять без нужды порядок и типы переменных в объекте: несовместимое изменение списка сбрасывает
   постоянные данные.
6. Проверить объём retain- и persistent-памяти ПЛК210 по документации ОВЕН (с учётом того, что экземпляр
   `FB_Totalizer` хранится целиком).
7. Проверить на стенде по таблице из шага 1: выключение питания, Reset Warm, Reset Cold, загрузка
   изменений, полная загрузка, Reset Origin.

### 4.3 Привязка ввода-вывода к ПЛК210

Что есть в коде. `GVL_IO` (папка `Converted`) — переменные с `AT` по пересчитанным адресам S7: биты
совпадают (`%I0.1` → `%IX0.1`), слова — номер байта S7 делится на 2 (`%IW64` → `%IW32`); `GVL_Markers` —
то же для меркеров. Это заготовка: на ПЛК210 каналы модулей привязываются в дереве устройств.

1. Добавить в дерево устройств модули ПЛК210 по конфигурации шкафа и составить таблицу: тег S7 и адрес
   (`samples/scl/PlcTags.csv`) → переменная `GVL_IO` → модуль и канал ПЛК210.
2. Привязать каналы на вкладке «Отображение входов/выходов» модуля одним из способов — **какой из них
   работает с переменными, у которых уже есть `AT`, сверить в IDE 3.5.17 с таргетом ПЛК210**:
   - адреса каналов модуля поставить равными адресам `AT` в `GVL_IO` (сгенерированный код не меняется);
   - каналы сопоставить с существующими переменными `GVL_IO` по имени, а `AT` убрать — это правка
     сгенерированного кода: её делают в проекте ПЛК210, а не в `src/`, или переносят в конвертер.
3. Сверить тип данных канала с типом переменной: аналоговые входы ОВЕН могут отдавать значение в своих
   единицах или `REAL`, а `FB_AnalogIn` ждёт `INT` 0…27648 (номинал S7). Варианты — масштабирование к
   0…27648 в рукописном слое ввода-вывода или замена NORM_X/SCALE_X на масштабирование ОВЕН
   ([methodology.md](methodology.md), «Масштабирование аналоговых сигналов»).
4. Порядок байтов: S7 — старший байт первым, ПЛК210 — младший. Слова, которые читаются побитно или
   собираются из байтов (`GVL_Markers`, пометки `addr.overlap`, `expr.slice_read`), проверить по одному.
5. Проверить на стенде каждый канал: дискретные — переключением, аналоговые — калибратором в точках
   4, 12, 20 мА и вне диапазона (обрыв, КЗ).

### 4.4 Прочее

- [ ] Свободный цикл для `MainTask`, если он нужен вместо 10 мс (`tools/codesys` создаёт только
      циклические задачи).
- [ ] Символьная конфигурация / OPC UA / Modbus для HMI и SCADA ([methodology.md](methodology.md), «Обмен с
      HMI», «Теги SCADA»).
- [ ] Функции неявной проверки (Add Object → POUs for implicit checks: `CheckDivDInt`, `CheckDivLInt`,
      `CheckBounds` и др.) — подключить на время наладки или записать, почему не нужны (пометки
      `expr.div_int`, MAPPING.md «Расхождения, которые конвертер не помечает»).
- [ ] Поведение после Stop → Start в CODESYS: флаг первого цикла не сбрасывается, код OB100 (`PRG_Startup`)
      и эмуляция `Initial_Call` не выполняются повторно — проверить, приемлемо ли это для объекта
      (в S7 каждый STOP → RUN — тёплый пуск с OB100).

## 5. После прогона тестов

1. `python tools/codesys/cds.py report` и разбор упавших тестов в [TEST_REPORT.md](TEST_REPORT.md)
   (разделы «Разбор результатов первого прогона», «Упавшие тесты»).
2. **F_TRIG на другой версии CODESYS или Standard** (например, на ПЛК210 с другим таргет-файлом). На
   3.5.17.30 со Standard 3.5.17.0 ложного спада на первом вызове нет (ASSUMPTIONS.md, запись S4 о
   семантике F_TRIG). Если падает тест `FB_S7FTrig_Test.StandardFTrigMatchesS7` или строка 1 сценария
   `FB_PumpAlternation/RotateOnStop` (`leadPump` = 2 вместо 1): в `s7conv/corpus.py` в `corpus_options`
   поставить `f_trig=M.S7COMPAT`, выполнить `python -m s7conv build-corpus`, повторить `cds.py test`, записать
   вывод в ASSUMPTIONS.md (записи S4 и K18 — семантика F_TRIG и выбор Standard `F_TRIG` для корпуса) и
   MAPPING.md (`fb.f_trig`).
3. Тесты `MatchesStandardInRealTime` сверяют таймеры S7Compat со Standard: расхождение — разобрать по
   семантике в объявлении блока (ASSUMPTIONS.md, запись K19 о семантике таймеров S7Compat), при
   необходимости поправить блок S7Compat.
4. Обновить таблицы «Последний прогон» в [STATIC_ANALYSIS.md](STATIC_ANALYSIS.md) результатами CI.

## 6. Экспорт перед коммитом

Правки в IDE допустимы только в рукописном коде (`S7Compat`, `tests/POUs/S7Compat`). Перед коммитом:

```bat
python tools\codesys\cds.py export --tests
git diff --stat
python -m s7conv build-corpus --check
```

Последняя команда должна пройти: если экспорт изменил сгенерированное, правку нужно перенести в
конвертер или корпус. Цикл «импорт → экспорт» без правок не должен давать диффа
(`python tools\codesys\cds.py roundtrip`).

Сопровождение самого репозитория (зеркало, превью для ссылок GitHub) — в
[CONTRIBUTING.md](../CONTRIBUTING.md), раздел «Сопровождение репозитория».
