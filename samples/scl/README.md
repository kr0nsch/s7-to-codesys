# Корпус SCL (`samples/scl/`)

Двадцать исходников SCL в стиле «внешних источников» TIA Portal (`.scl`, «Generate source from blocks»),
написанных с нуля для этого проекта. Объект вымышленный — ВОС «Северная»: насосная станция II подъёма,
скорые фильтры с промывкой, дозирование реагента. Кода Siemens, примеров из документации и чужих
репозиториев здесь нет.

Корпус — вход конвертера SCL → ST и материал для проверки поведения: у шести блоков есть сценарии
`scenarios/<Блок>.csv` (см. [scenarios/README.md](../../scenarios/README.md)), ожидаемые значения которых
посчитаны по описанию логики в заголовке файла, а не по результату конвертации.

> **Честно о проверке.** TIA Portal в окружении проекта нет: исходники не компилировались в TIA.
> Синтаксис написан по знанию автора о формате выгрузки TIA Portal V15–V18. Места, в которых автор не
> уверен (состав входов стартовой информации OB, точные имена параметров системных функций), помечены
> в заголовках файлов «сверить с документацией TIA Portal». На работу конвертера это не влияет:
> грамматика строится по этому корпусу, а цель «скомпилировать в TIA» не ставится.

## Чем файлы отличаются от настоящей выгрузки

- Кодировка UTF-8 **без** BOM, переводы строк LF, отступы пробелами (правила репозитория). Парсер должен
  принимать и BOM, и CRLF, и табы — их можно встретить в настоящих выгрузках.
- Каждый файл начинается с комментария `//` перед ключевым словом блока: назначение, нормативное описание
  логики, что проверяет файл. В выгрузке TIA такого заголовка нет (комментарий блока идёт после `VERSION`,
  он тоже есть).
- Комментарии по-русски, идентификаторы — ASCII. Имена переменных — в стиле S7 (`camelCase` без
  префиксов типа), а не по соглашениям CODESYS из `CONTRIBUTING.md`: конвертер имена не меняет (на них
  завязаны HMI и SCADA), поэтому сконвертированный код линтер `STL007` пропускать не будет — это
  решение интеграции (исключение или отдельный каталог), а не ошибка корпуса.

## Данные проекта вне исходников

Часть сведений TIA Portal в исходники SCL не выгружает. Для конвертера они лежат рядом (CSV — UTF-8,
разделитель — запятая, первая строка — заголовок):

- `PlcTags.csv` — таблица тегов ПЛК, как её экспортирует TIA Portal (подмножество столбцов):
  `Name, Path, Data Type, Logical Address, Comment`. Все символьные имена `"Тег"` из кода и все
  абсолютные адреса `%I/%Q/%IW/%QW/%M/%MW/%MD/%T` корпуса в ней есть; в коде к одному адресу
  обращаются и символьно, и абсолютно (`"P101_ThermalOk"` и `%I0.2`) — конвертер должен свести их
  к одной переменной слоя ввода-вывода.
- `BlockProperties.csv` — свойства блоков: `Block, Kind, Number, Source, Optimized, Event,
  CycleTime_ms, Phase_ms, Priority, Comment`. Здесь номера DB (код обращается к `DB30` и `DB40` по
  номеру), номера OB и класс события, период и приоритет циклического OB. Значения приоритетов —
  настройки вымышленного проекта; допустимые диапазоны для конкретного CPU сверить с документацией.
  `DB_Archive` (DB40) есть только в таблице: исходника нет, к нему обращаются только по номеру.
- `ob_config.json` — те же номера, вид и период OB в формате параметра `--ob-config` конвертера
  (`{"Имя OB": {"number": 30, "kind": "cyclic", "interval_ms": 100}}`). Приоритет задачи CODESYS сюда
  не записан: шкалы приоритетов S7 и CODESYS обратные, выбор — за конвертером.

Порядок зависимостей при чтении корпуса: `UDT_PlantTypes` → FC и FB (`FB_Valve` использует
`FB_Debounce`) → `DB_Plant` (экземплярные DB ссылаются на FB) → OB.

## Намеренно трудные и непереносимые конструкции

Они нужны, чтобы отчёт конвертера показывал честные границы автоматизации. Ожидаемое поведение
конвертера — комментарий `// MIGRATION-TODO:` с причиной, а не «тихий» перевод.

| Конструкция | Где | Почему не переносится автоматически |
|---|---|---|
| AT-наложение (`statusBits AT statusCopy : Array[0..15] of Bool`) | `FB_LegacyTelegram` | в CODESYS нет наложения переменных в ФБ; замена — `UNION` или битовый доступ `.n`, выбор зависит от использования |
| `Any` и разбор ANY-указателя через AT-структуру | `FB_LegacyTelegram` | формат ANY (10 байт) — особенность S7; в CODESYS — `POINTER`/`ANY` с другой семантикой |
| `P#DB30.DBX4.0 BYTE 16`, `P#M100.0 BYTE 16` | `FB_LegacyTelegram`, `OB_Main` | указатели на абсолютные области; нужен перенос данных в переменные и `MemCpy`/`ADR` |
| `BLKMOV` | `FB_LegacyTelegram` | системная функция S7 (SFC20) |
| `%DB30.DBW0`, `WORD_TO_BLOCK_DB(...).DW[...]` | `FB_LegacyTelegram` | абсолютная и косвенная адресация DB по номеру; номеров DB в CODESYS нет |
| `S_ODT` с номером таймера `"T_Retry"` (%T5), `S5Time` | `FB_LegacyTelegram` | таймеры S5 — ресурсы CPU; замена — `TON`, разрешение S5Time (10 мс…10 с) теряется |
| `GOTO` и метки | `FB_LegacyTelegram` | в ST CODESYS есть `JMP`, но перенос меняет структуру; лучше переписать |
| `ENO := FALSE` | `FB_LegacyTelegram` | у POU CODESYS на ST нет ENO; нужен явный выход ошибки |
| `Variant`, `TypeOf`, `VariantGet` | `FB_EventLogger` | в CODESYS — `ANY`/`__VARINFO` с другой моделью |
| `RD_SYS_T`, `WR_SYS_T`, `RUNTIME` | `FB_EventLogger`, `OB_Startup` | системные функции; в CODESYS — библиотеки SysTime/CAA, не Standard |
| `PEEK`, `POKE` | `FB_EventLogger` | прямой доступ к памяти по номеру DB и смещению |
| `%IW272:P` | `OB_Main` | прямой доступ к периферии мимо образа процесса |
| `HW_ANY`, OB82 «Diagnostic error interrupt» | `OB_Startup` | диагностика модулей в CODESYS устроена иначе (драйверы ввода-вывода) |
| OB100 «Startup», `LostRetentive`, `LostRTC` | `OB_Startup` | OB запуска в CODESYS нет: флаг первого цикла, FB_init или системное событие — решение вручную |
| DTL | `DB_Plant`, `OB_Startup` | тип S7-1200/1500; ближайший аналог — `DT` или структура |

## Подводные камни поведения, заложенные в корпус

Это не ошибки корпуса, а места, где дословный перевод может изменить поведение. Сценарии ловят
часть из них.

- **F_TRIG на первом вызове.** В описании `FB_PumpAlternation` спада на первом вызове нет (так ведёт
  себя F_TRIG S7: память фронта в начале FALSE). Начальное состояние памяти F_TRIG в стандартной
  библиотеке CODESYS **сверить с источником**; первая строка сценариев `FB_PumpAlternation` это проверяет.
- **Обновление таймеров IEC.** В модели сценариев выходы таймера обновляются только при его вызове.
  У S7-1500 выходы IEC-таймера, по сведениям автора, обновляются и при обращении к ним (сверить с
  документацией TIA Portal); блоки корпуса читают Q/ET только сразу после вызова, поэтому разница не
  проявляется.
- **`CTU_INT` → `CTU`.** У CODESYS Standard вход сброса называется `RESET`, PV и CV — тип WORD
  (см. замену R12 в `tools/README.md`), у S7 — `R` и Int.
- **Именованные параметры `LIMIT(MN:=, IN:=, MX:=)`, `MIN/MAX(IN1:=, IN2:=)`.** Операторы CODESYS
  вызываются позиционно.
- **`SCALE_X` с результатом Int** (`OB_Cyclic`) — округление или отсечение при переводе REAL → INT
  выбрать явно.
- **Данные двух задач.** `DB_PT101` вызывается в OB1, а читается в OB30; `DB_FT101` — наоборот.
  В CODESYS задачи с разным приоритетом тоже прерывают друг друга — нужна проверка согласованности.
- **Константа периода** `CYCLE_TIME` в OB30 должна совпадать с интервалом задачи — договорённость,
  а не проверяемое свойство.
- **Сохраняемые данные.** `VAR RETAIN` в `DB_Plant` и `FB_Totalizer`: в CODESYS выбрать `RETAIN`
  или `PERSISTENT` (поведение при загрузке программы разное).
